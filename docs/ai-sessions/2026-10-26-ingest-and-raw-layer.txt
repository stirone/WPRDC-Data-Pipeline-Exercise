● The three-table structure (run, then attempt, then resource) is right, and
  logging each retry as its own row is the most important part. A few changes
  would make it fit the failures you actually saw.

  1. Drop ckanapi for the fetching. It hides what you want to record. When it
  gets a blank or HTML response it raises a generic error, and you lose the
  status code, headers and body. It also doesn't tell you about retries. Use
  requests (or httpx) with a small retry wrapper of your own, so every attempt
  goes through code that logs it. This also helps in the interview, because you
  can explain every line.

  2. Classify each attempt by what came back, not by the HTTP status. Your two
  failures were probably HTTP 200 responses. A blank body and an HTML page
  served as a 200 are classic signs of a proxy or gateway problem. The outcome
  categories should come from checking the response:
  - ok
  - empty_body
  - non_json (the content-type or parse doesn't match)
  - ckan_error (valid JSON, but CKAN returned "success": false)
  - http_error
  - timeout
  - connection_error

  For that you need to store content_type, content_length, and whether the body
  parsed. The 500-character snippet is a good idea, and it matters most for
  exactly these cases.

  3. Record the request itself. Store the endpoint, the parameters (resource_id,
  offset/limit or SQL) and the page number. Without them you can't tell whether
  failures cluster on large offsets, which is a common pattern with CKAN
  datastore paging.

  4. Make fetch_resource carry the update-detection data. Capture the resource's
  last_modified, the package's metadata_modified, the record count CKAN
  reports, and a SHA-256 of what you landed. That gives you most of the "how
  would you handle updates" answer: if the metadata hasn't changed, skip the
  fetch; if the hash is the same, skip the reload.

  5. Treat "raw" as the files you fetched, not only a table. The requirement is
  to land raw data unchanged. The most faithful version is the response bytes
  written to disk, under a path that includes the run ID, with fetch_resource
  pointing to that file and its hash. The raw DuckDB table is then built from
  that file. This also lets you rebuild everything without hitting the shaky API
  again.

  6. Think about the fetch strategy. Property sales is a large dataset, so
  paging through datastore_search means hundreds of requests, and each one is a
  chance to fail. Paging by offset can also skip or duplicate rows if the data
  changes partway through. CKAN's bulk dump endpoint
  (/datastore/dump/<resource_id>) gets the whole thing in one request. I'd test
  both and let your fetch log tell you which is more reliable. That would make a
  strong README point backed by evidence.

  7. Smaller points:
  - Store timestamps in UTC. v_reliability_by_hour will mislead if you mix local
    time and UTC.
  - Write each attempt row as soon as it happens, so a crash still leaves the
    evidence behind.
  - DuckDB allows only one writer. If you have the database open in the DuckDB
    CLI while the pipeline runs, the pipeline's writes will fail. Close the CLI
    first, or open it read-only.
  - Put the logging tables in their own schema (e.g. ops.*) in the same database
    file, separate from raw.* and the cleaned layer.
  - The two views are fine for development. Just don't let reliability analysis
    take time away from the required parts.

  If you'd like, I can draft the revised schema and the fetch-and-log module
  next. Then you can start collecting real attempt data right away while we
  explore the dataset.

  SELECT endpoint, count(*) AS requests,

    reader can still block a writer.

  What gets smaller is what you store and process in DuckDB.

  Reducing the download would need filtering on the server, for example
  datastore_search_sql ... WHERE "RECORDDATE" >= <last cutoff>. I'd reject that
  for this exercise:
  - It misses corrections and deletions to older records.
  - It relies on the SQL endpoint, which is the flakiest part of the API.
  - The full download only takes about 12 seconds.

  It belongs in the README's 100x-scale section, along with a weekly full
  reconciliation to catch what the filter misses.

  Keeping every downloaded CSV, as you want, also fits: the files are the "raw
  data, unchanged" the requirements ask for, so the database table no longer has
  to be a full copy of each snapshot.

  How the incremental load would work

  row_hash: an MD5 of the 25 non-_id columns, joined with a separator that can't
  appear in the data, and with NULL encoded so it differs from an empty string.
  MD5 is fine here because we're detecting changes, not doing security.

  raw.property_sales becomes a history table, one row per distinct row version:

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │        column        │                     meaning                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ row_hash             │ primary key                                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ the 25 source        │ verbatim text, as now                            │
  │ columns              │                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ _id                  │ kept for reference only                          │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ first_seen_snapshot  │ the snapshot where this version first appeared   │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ removed_in_snapshot  │ the snapshot where it disappeared (NULL while    │
  │                      │ it's still current)                              │
  └──────────────────────┴──────────────────────────────────────────────────┘

  For each new snapshot:
  1. Hash the file's rows into a temporary table.
  2. Insert hashes we haven't seen before, which are new rows or new versions of
     changed rows.
  3. Close any current hashes that are missing from the file, which are
     deletions or old versions of changed rows.
  4. Leave unchanged rows alone.

  Results:
  - The first load stores 506k rows. After that, each day only adds what
    changed.
  - Any past snapshot can be rebuilt as the rows where first_seen <= S and
    (removed_in is NULL or later than S).
  - Re-running a snapshot finds nothing new and nothing to close, so it changes
    nothing.

  One limitation: when a record is edited, for example a price correction, it
  shows up as one hash closed and another inserted. To link the two as an update
  to the same sale, you need a business key, which is the natural-key work
  still ahead. One candidate is PARID + SALEDATE + RECORDDATE + PRICE + DEEDBOOK
  + DEEDPAGE + SALECODE. It's unique today, but it includes PRICE, so it can't
  recognize a price correction. PARID + DEEDBOOK + DEEDPAGE is worth testing.

  New quality check: no duplicate row_hash within a single snapshot. There are
  none today, but if two identical rows ever appear, the history table can't
  tell them apart, so the load should fail loudly.

  Two more data findings from this pass

  - RECORDDATE has a minimum of 0212-08-01, presumably a typo for 2012.
  - RECORDDATE has a maximum of 2026-10-29, three days after today.

  Both are good candidates for quality checks written specifically because of
  this dataset.

  Should I go ahead and replace the full-snapshot table with this history table?
  It would also keep raw.property_sales_snapshot as the ordered list of
  snapshots and update the tests.

  daily changes it would be about 185M rows. DuckDB stores data by column and
  compresses it, and these columns are highly repetitive (city names, sale
  codes, the same addresses every day), so that's likely a few GB. It's fine on
  a laptop, but it's the first thing to change at 100x scale.

  If you want the benefits of hashing while keeping full snapshots:
  1. Add a row_hash column to raw.property_sales, computed at load time. Each
     snapshot stays complete and readable on its own, and comparing two days
     becomes a simple set comparison: hashes in day B but not day A are new or
     changed rows, and the reverse are removed or changed rows. You'd get change
     tracking for analysis and quality checks without the history table's
     bookkeeping. For example, a check could fail if a daily refresh drops more
     than 1% of rows.
