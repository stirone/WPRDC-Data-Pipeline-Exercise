● python -m pytest runs the project's automated checks. Pytest finds every
  test_*.py file in tests/, runs each def test_... function in them, and reports
  which passed and which failed. There are 109 tests, and they take about two
  minutes.

  Each test builds a small, made-up dataset in a temporary database, runs one
  piece of the pipeline on it, and checks the result. None of them contact the
  real WPRDC site or use your real database. So a passing run means the code
  behaves as designed, not that today's real data is good.

  Here's what each file covers, in the order the pipeline runs:

  File: test_http_client.py (tests/test_http_client.py)
  What it checks: Downloading from the WPRDC API. When the server sends back a
  bad answer (a blank reply, or a "504 Gateway Timeout" error page), the code
  retries and logs every attempt. It also gives up after the maximum number of
  tries, and a failed download doesn't leave a half-written file behind.
  ────────────────────────────────────────
  File: test_ingest.py (tests/test_ingest.py)
  What it checks: Fetching the file. If the file hasn't changed since the last
  fetch, nothing is reloaded. A file that fails validation is still archived
  and recorded.
  ────────────────────────────────────────
  File: test_load_raw.py (tests/test_load_raw.py)
  What it checks: Loading the CSV into the raw tables. Values are kept exactly
  as
  they arrived, and loading the same file twice doesn't create duplicates. If
  the columns change (schema drift) or the row count doesn't match, the load
  stops and nothing is saved. The raw tables can be rebuilt from the archived
  files.
  ────────────────────────────────────────
  File: test_transform.py (tests/test_transform.py)
  What it checks: Cleaning the data. Prices and dates are parsed correctly,
  extra
  spaces are trimmed, and blank values become empty (null). Rows that fail a
  quality check are held out ("quarantined") of the clean table. Running the
  step twice changes nothing.
  ────────────────────────────────────────
  File: test_checks.py (tests/test_checks.py), test_dq.py (tests/test_dq.py)
  What it checks: The data-quality rules themselves, for example a missing or
  unparseable record date, sale dates before 2012, and possible duplicate
  records. Each rule must have a unique ID and a version that changes when its
  logic changes.
  ────────────────────────────────────────
  File: test_dq_issues.py (tests/test_dq_issues.py)
  What it checks: Tracking a data problem over time. An issue stays open across
  downloads until it's fixed, replaced by a corrected record, or removed. It's
  closed if the rule changes, and reopened if the problem comes back.
  ────────────────────────────────────────
  File: test_dq_alerts.py (tests/test_dq_alerts.py)
  What it checks: When an alert fires: a sharp jump in a rule's failure rate
  does, and a small rise doesn't. Duplicate-key problems alert right away.
  Re-running doesn't send the same alert twice.
  ────────────────────────────────────────
  File: test_sale_classes.py (tests/test_sale_classes.py)
  What it checks: Grouping sale codes into the six classes (market, family,
  estate, distressed, and so on). Every code has to be mapped.
  ────────────────────────────────────────
  File: test_analytics.py (tests/test_analytics.py)
  What it checks: The final output table: the ward-level rollup, parcel details
  taken from each parcel's latest sale, and that the output view's columns
  match its documentation. Rebuilding gives an identical result, and if a build
   fails, the previous tables are kept.
  ────────────────────────────────────────
  File: test_pipeline.py (tests/test_pipeline.py)
  What it checks: The python -m wprdc.pipeline command. Steps run in order, a
  failing step stops the ones after it, and a full end-to-end run works against
   a fake version of the WPRDC API.

  If you run python -m pytest -v instead, it prints each test's name with PASSED
  or FAILED next to it, which makes the output easier to follow.

  2. Changing record_date_missing from quarantine to flag

  The code change is one word, at checks.py:75 (wprdc/checks.py#L75):
  action="quarantine" becomes action="flag". You'd also remove the "Quarantined
  with misgivings" comment above it (checks.py:67-70 (wprdc/checks.py#L67-L70)).
  The system was built so this change is safe.

  Why it's safe: a check's version is a hash of its where condition only.
  Changing action doesn't change the version, so:

  - The 1,248 open issues stay open. Their action column changes to flag on the
    next transform, with no "fixed" or "rule_changed" closings.
  - There is no definition_changed notice, and the rate history isn't reset.
  - Past evaluations in dq.check_run and dq.check_result still show quarantine.
    That's correct, because those columns record the action as it was defined at
    the time.

  You don't need new data for it to take effect. Running python -m
  wprdc.pipeline again works even if the source hasn't changed. Ingest skips the
  download, the transform finds the checks already evaluated for this snapshot
  and brings the issue list up to date, and then transform.py:129-140
  (wprdc/transform.py#L129-L140) rebuilds the clean table using each check's
  current action. The 1,248 rows then enter clean.property_sales with dq_flags =
  ['record_date_missing'], and analytics picks them up.

  One small quirk: for this one snapshot, dq.check_run will still say quarantine
  while the clean table treats the rows as flagged. That clears up from the
  next new snapshot on.

  ▎ Changing or adding a check
  ▎
  ▎ Checks are changed in code by the engineer and reviewed through git. After
  ▎ any change, run python -m wprdc.pipeline. The new definitions apply to the

  ▎
  ▎ To change a check from quarantine to flag (for example,

  ▎ wprdc/checks.py. On the next run, its records move into clean.property_sales
  ▎ with the check's name in dq_flags, and its open issues stay open with their
  ▎ action updated. The tests don't depend on any check's action, so python -m

  ▎

  ▎
  ▎ To add a check, append a Check to CHECKS with:
  ▎ - an id
  ▎ - a description
  ▎ - an action (quarantine or flag)

  ▎ failing records. A subquery refers to that table as typed.
  ▎
  ▎ Set alert="any" if the check should normally find nothing and should alert
  ▎ on its first failure. Add a test for the condition in tests/test_dq.py.
  ▎
  ▎ To remove a check, set retired=True. Don't delete it, so its history stays
  ▎ readable.
