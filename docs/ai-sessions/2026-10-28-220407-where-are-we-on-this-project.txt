● You don't need to build anything. DuckDB 1.5.6 comes with a browser-based SQL
  notebook, the DuckDB UI, which is the browse tool you're describing. A
  home-made web page would just be more code to maintain and explain in the
  interview, and it would do less than the UI does.

  Option 1: the DuckDB UI (recommended)

  In the project folder, run:
  duckdb -ui
  A page opens at http://localhost:4213. In the first cell, attach the database
  read-only:
  ATTACH 'data/wprdc.duckdb' AS wprdc (READ_ONLY);
  USE wprdc;
  Read-only matters. DuckDB lets only one process write to the file at a time,
  so if the UI opened it read-write, python -m wprdc.ingest and load_raw would
  fail while the UI is running.

  The UI gives you:
  - a table browser in the left sidebar
  - column summaries for each result (value distributions, null counts)
  - notebook cells you can save

  Two things to know:
  - The first launch installs the ui extension from the internet.
  - The page's interface is served from DuckDB's (MotherDuck's) site, but
    queries run and data stays on your machine.

  Option 2: the plain CLI

  duckdb -readonly data/wprdc.duckdb
  Then, at the D prompt:
  .mode box
  .maxrows 50
  SUMMARIZE raw.property_sales_latest;           -- every column: min/max,
  distinct count, null %
  SELECT * FROM raw.property_sales_latest LIMIT 20;
  Type .quit to exit.

  What's in the database

  ┌────────────────────────────────────────────┬────────────────────────────┐
  │                   Object                   │         What it is         │
  ├────────────────────────────────────────────┼────────────────────────────┤
  │ raw.property_sales_latest                  │ Today's snapshot (506,726  │
  │                                            │ rows). Start here.         │
  ├────────────────────────────────────────────┼────────────────────────────┤
  │ raw.property_sales                         │ All snapshots. Filter with │
  │                                            │  WHERE snapshot_id = ....  │
  ├────────────────────────────────────────────┼────────────────────────────┤
  │                                            │ Snapshot list and the      │
  │ raw.v_snapshots, raw.v_snapshot_changes    │ differences between        │
  │                                            │ snapshots.                 │
  ├────────────────────────────────────────────┼────────────────────────────┤
  │ ops.v_request_outcomes,                    │                            │
  │ ops.v_failure_breakdown,                   │ The fetch logging.         │
  │ ops.v_reliability_by_hour                  │                            │
  └────────────────────────────────────────────┴────────────────────────────┘

  Every source column is stored as text, because the raw layer keeps values
  exactly as they arrive. To do arithmetic, convert first, e.g. TRY_CAST(PRICE
  AS INTEGER). Converting the types is the cleaned layer's job.

  Here are a few queries that bear on choosing a question:
  -- What kinds of sales are there?  ($1 transfers, multi-parcel sales, etc.)
  SELECT SALECODE, SALEDESC, count(*) n FROM raw.property_sales_latest GROUP BY
  ALL ORDER BY n DESC;

  -- Sales by municipality
  SELECT MUNIDESC, count(*) n, median(TRY_CAST(PRICE AS INTEGER)) median_price
  FROM raw.property_sales_latest GROUP BY ALL ORDER BY n DESC;

  -- Gap between the sale date and the date the deed was recorded
  SELECT date_diff('day', TRY_CAST(SALEDATE AS DATE), TRY_CAST(RECORDDATE AS
  DATE)) gap_days, count(*)
  FROM raw.property_sales_latest GROUP BY ALL ORDER BY 2 DESC LIMIT 20;

● To decide an outcome, the pipeline has to look at the full data for the
  snapshot where the problem went away. The fix is to make that decision once,
  while the data is still there, and store the answer.

  Why the outcome needs the full data. Take a flagged record: parcel X, deed
  16294/325, sale date 2018-08-17, recorded 2008-08-17. In the next snapshot it
  isn't flagged any more. To say why, the pipeline has to look in that snapshot:
  - Is the record still there, unflagged? Then it was fixed.
  - Is it gone, but a record with the same deed is there? Then it was replaced,
    for example because the date was corrected.
  - Is it gone with nothing like it? Then it was removed.

  All three answers need the snapshot's full 506,000 rows, not only the list of
  flagged records.

  The problem with my first version. I had made the steward's list a view. A
  view is a saved query that recalculates every time someone opens it. So each
  time the steward opened the list, it would go back to the raw snapshots to
  answer those three questions again.

  The raw layer, however, lets you prune old snapshots: delete their rows from
  the database to save space, keeping only the CSV files. Once the snapshot
  where an issue was resolved had been pruned, the view would have nothing to
  look in. Those resolved issues would lose their outcome, or the view would
  fail.

  The fix. The outcome is now decided once, when the pipeline checks a new
  snapshot, while that snapshot's rows are definitely in the database. The
  answer is stored in a small table, dq.issue_resolution, which says which
  issue, which snapshot resolved it, the outcome, and the replacing record if
  there is one. The steward's list reads that stored answer, so pruning raw
  snapshots later doesn't affect it.

  This doesn't make rebuilds give different answers. The outcome still depends
  only on the snapshot and the check definitions, so rebuilding from the archive
  produces the same result.

● The raw layer is the part of the pipeline that keeps the data exactly as WPRDC
  delivered it, before any typing, trimming or checks. In this project it's
  stored at two levels, and pruning only touches one of them.

  The two levels of "raw"

  1. The CSV archive (data/raw/.../dump/*.csv). This is the permanent record.
  - Every successful download is saved as a file and never changed or deleted.
  - Each file is about 105 MB. There are 3 so far (314 MB).
  - Every file traces back to a logged fetch in ops.fetch_resource.

  2. The raw tables in DuckDB (raw.property_sales). This is a working copy.
  - Each distinct CSV is loaded once as a snapshot: all ~506,000 rows, every
    column still text, tagged with that file's snapshot_id and a row hash.
  - Snapshots are never edited. Each one is the complete dataset as of one
    download.
  - A snapshot takes roughly 35–40 MB inside DuckDB (the database is 79 MB
    holding two).

  Everything downstream is built from level 2. The cleaned layer and the checks
  are rebuilt from it, and none of them change the raw data.

  What the snapshots in DuckDB are for

  - Viewing any day's data: WHERE snapshot_id = ... returns the dataset exactly
    as it was on that day. This is why you rejected the history table.
  - Comparing snapshots: raw.snapshot_diff() and v_snapshot_changes showed the
    204 sale-code reclassifications between Oct 26 and Oct 28.
  - Re-running the cleaned layer: when you change a rule, you can rebuild from
    data that is still exactly as it arrived.

  Pruning

  At one snapshot per day, the DuckDB copy grows by about 14 GB a year. The CSV
  archive grows by about 38 GB.

  python -m wprdc.load_raw --prune-keep 30 deletes the rows of all but the 30
  most recent snapshots from DuckDB. The catalog entry stays, marked pruned_at,
  and the CSV stays on disk. --rebuild reloads everything from the CSVs, so
  pruning can always be undone.

  Nothing prunes automatically today. It's a command you choose to run. With
  daily refreshes in production, you'd probably run it on a schedule: keep a
  month or so of snapshots ready to query and leave the older ones in the
  archive.

  How this connects to the data quality design

  The checks only ever run against the latest snapshot, which is never pruned.
  But an issue's history spans many snapshots: first seen on Oct 26, resolved on
  Nov 15, and so on.

  - The first version worked out "fixed / replaced / removed" whenever someone
    opened the steward's list, by looking in the snapshot where the issue was
    resolved. Two months later, after pruning, that snapshot's rows would be
    gone from DuckDB. You'd have to run --rebuild just to read the list.
  - The revised version makes that decision on the day the snapshot is checked,
    while its rows are certainly there, and writes the answer down. After that,
    the steward's list never needs the old raw rows again, however much you
    prune.

  In short: the CSVs are kept forever, the DuckDB snapshots are a pruneable
  working copy, so anything we'll need to know long-term about a snapshot should
  be worked out and saved while it's loaded.

● Not strictly. Nothing depends on it for correctness, and the data quality
  design doesn't use it at all. Here's what it does, what it costs, and what
  replacing it would look like.

  Where it's used (from searching the code):
  - raw.snapshot_diff(), which lists the rows added and removed between two
    snapshots
  - raw.v_snapshot_changes, which counts them per snapshot

  That's all. The hash is md5 of every source column except _id. It works as a
  fingerprint of a row's content, so comparing two snapshots becomes a join on
  one column instead of 24.

  What it costs: it's the largest column in the raw table, about 9 MB per
  snapshot, or roughly 20% of raw storage. Hashes look random, so they don't
  compress.

  What we'd lose without it: nothing we couldn't rebuild. At 500,000 rows,
  DuckDB can compare snapshots across all columns directly:
  SELECT * EXCLUDE (snapshot_id, source_row_number, row_hash, _id) FROM
  raw.property_sales WHERE snapshot_id = :new
  EXCEPT ALL
  SELECT * EXCLUDE (snapshot_id, source_row_number, row_hash, _id) FROM
  raw.property_sales WHERE snapshot_id = :old
  That gives the same answer and runs in about a second at this size. A third
  option is to compute the hash inside the comparison query instead of storing
  it.

  Where it would earn its place:
  - At 100x scale, a one-column join is much cheaper than comparing every
    column, and a stored fingerprint lets you detect changed rows without
    re-reading old data. That's a natural point for the README's scaling
    section.
  - Together with the record key: "same key, different hash" is the simplest
    definition of this record was updated. That's exactly how we found the 204
    sale-code reclassifications.

  **1. If a check changes and then changes back on the same snapshot,
  quarantined records drop off the steward's list.** (wprdc/dq.py:1239-1243 in

  - **Cause:** `evaluate` does `continue` when a `check_run` row already exists
  for (eval, check, version), so `update_issues` is skipped.

  reloading the rows.

  `raw.property_sales_latest` are at A.
