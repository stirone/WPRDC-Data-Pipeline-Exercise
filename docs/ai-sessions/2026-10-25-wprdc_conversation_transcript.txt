USER (voice):
Tell me more about DuckDB because I have not used it.

ASSISTANT:
Sure, you'll pick it up fast. DuckDB is basically SQLite for analytics. It's an in-process database: no server and no install beyond pip install duckdb, and the whole database lives in one file in your repo folder. But where SQLite stores data row by row, DuckDB is columnar and vectorized like Spark or Synapse, so aggregations over millions of rows are very fast on a laptop.

A few things make it great for this exercise:

- Direct file queries. It can read CSV, Parquet or JSON directly, even from a URL, with something like SELECT * FROM read_csv_auto('file.csv'). The schema is inferred for you.
- Postgres-flavoured SQL. For you coming from T-SQL, it'll feel familiar, with nice extras like QUALIFY for window filtering.
- Upserts. It supports INSERT OR REPLACE and INSERT ... ON CONFLICT, which covers your re-runnable requirement.
- Python integration. It works smoothly with pandas, and dbt has a DuckDB adapter if you want models and tests.

Your workflow would be: pull the data from the CKAN API in Python, land it as raw tables or Parquet, then do the transforms and quality checks in DuckDB SQL.

USER:
To pull down this data programatically using the CKAN API, do I need an API token?

ASSISTANT:
No. Reading public datasets on WPRDC needs no token or account, so plain unauthenticated GET requests work. In CKAN, API tokens are only for writing data or reading private datasets, neither of which applies here.

That's good for the exercise, too: a reviewer can clone your repo and run it without setting up any credentials.

A few practical notes for the pull:

- Paging. datastore_search returns 100 rows by default, so loop with limit and offset. Each response includes a total, so you know when you're done. For a big table like property sales, downloading the resource's bulk CSV URL in one request is often simpler and faster.
- Change detection. Call resource_show first and compare its last_modified against what you stored on the previous run, then skip the pull if nothing changed.
- Be polite. Set a descriptive User-Agent, add retries with backoff, and set a timeout. A public portal can be slow or briefly unavailable, and graceful handling of that is a nice touch the reviewers will notice.

ASSISTANT:
I can't know for sure, but two explanations fit best.

1. You caught the table mid-reload. Some CKAN publishers refresh a datastore table by clearing it and reloading it, which leaves a window where the API returns success with zero rows. If both empty runs were close together, and the later ones were a few minutes after, that fits.
2. A cached empty response. WPRDC sits behind a proxy or CDN, and if an empty response got cached, you'd keep getting it until the cache expired.

Either way, the server said "success, nothing here" rather than failing, since an error would have raised an exception in ckanapi. One quick check: did result['total'] also show 0 on those runs? If so, the server really thought the table was empty at that moment.

To see more about each request, two things help. First, turn on HTTP logging, since ckanapi uses requests under the hood:

    import logging
    logging.basicConfig(level=logging.DEBUG)  # shows each request, URL and status code

Second, for full detail, make one call with requests directly so you can see status, timing and cache headers:

    import requests

    r = requests.get(
        "https://data.wprdc.org/api/3/action/datastore_search",
        params={"resource_id": "4ab1e23f-3262-4bd3-adbf-f72f0119108b", "limit": 5},
        headers={"User-Agent": "allegheny-screening-exercise/0.1"},
        timeout=30,
    )
    body = r.json()
    print(r.status_code, r.elapsed)
    print({k: v for k, v in r.headers.items() if k.lower() in ("date", "age", "cache-control", "x-cache", "cf-cache-status")})
    print("total:", body["result"]["total"], "returned:", len(body["result"]["records"]))

An Age header or a cache-status of HIT points to caching. A fresh response with total: 0 points to a reload in progress. You can also call resource_show on the same ID and look at last_modified and datastore_active to see whether the publisher just touched it.

This is also a gift for the exercise. It's exactly the kind of "something you found in this dataset" that makes a strong quality check: if a pull comes back with zero rows, or far fewer than last time, fail loudly instead of overwriting your cleaned layer with nothing. USER:
so, it's just "pip install duckdb"?  how do I use it then?

ASSISTANT:
Yes, pip install duckdb is it. There's no server to start and nothing to configure. It's a library you import, like sqlite3.

Basic use in Python:

    import duckdb

    con = duckdb.connect("pipeline.duckdb")  # creates the file if it doesn't exist; omit the name for in-memory

    con.sql("CREATE TABLE IF NOT EXISTS demo (id INTEGER, name VARCHAR)")
    con.sql("INSERT INTO demo VALUES (1, 'Allegheny'), (2, 'Pittsburgh')")
    con.sql("SELECT * FROM demo").show()  # prints a nice table in the terminal

    df = con.sql("SELECT * FROM demo").df()  # or pull results into pandas
    con.close()

Querying files directly, with no load step:

    con.sql("SELECT * FROM read_csv_auto('sales.csv') LIMIT 5").show()
    con.sql("SELECT * FROM 'raw/*.parquet'").show()  # globs work too

Loading what you pull from CKAN. The cleanest pattern for your exercise is to land the API records as-is, then transform in SQL:

    import pandas as pd

    records = body["result"]["records"]  # from your datastore_search call
    raw_df = pd.DataFrame(records)

    con.sql("CREATE OR REPLACE TABLE bronze_sales AS SELECT * FROM raw_df")  # DuckDB sees local pandas variables by name

That last trick surprises most people: DuckDB can query a pandas DataFrame just by using its variable name in the SQL. From there you write your silver and gold layers as plain SQL views or tables.

Optional CLI. If you want a SQL prompt like SSMS-lite, install the standalone CLI (winget install DuckDB.cli on Windows), then run duckdb pipeline.duckdb to poke at your tables interactively. For a GUI, DBeaver connects to DuckDB files too.

One gotcha: only one process can open a .duckdb file for writing at a time. If your script errors with a lock message, close the CLI or DBeaver session that has the file open.
